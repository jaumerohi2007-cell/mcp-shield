# Security & Privacy Whitepaper

This document is designed to answer common security, privacy, and operational questions from IT and Security departments (CISOs) evaluating the deployment of **MCP-Shield** in a corporate environment.

## 1. Data Privacy and Egress (Data Exfiltration)

**Q: What data leaves the developer's machine and goes to the cloud?**
A: **Almost nothing.** MCP-Shield operates as a local proxy on the developer's machine (`localhost`). The cloud component (`mcp-shield-server`) is used exclusively for **telemetry metadata** and rule synchronization.

The following data **DOES NOT** leave the machine:
- The contents of source code files.
- The prompts typed by the developer into the AI.
- The responses generated by the LLM.
- Output from terminal commands (stdout/stderr) unless explicitly blocked and logged as an incident snippet (maximum 100 characters for context).

The following data **DOES** leave the machine for SOC2 compliance logging:
- Developer Email / Team ID.
- Timestamp of the action.
- The name of the tool executed (e.g., `run_command`, `write_file`).
- A sanitized snippet of the command executed (e.g., `npx jest`).
- The verdict (`allowed`, `blocked`, `ask`).

## 2. Cloud Outage Resilience (High Availability)

**Q: What happens if the MCP-Shield cloud server goes down? Does it block the developers' AI tools?**
A: **No.** MCP-Shield is designed with a **Local-First Architecture**. 
When a developer logs in, their organization's security rules are downloaded and cached locally on their machine. If the cloud server (`mcp-shield-server`) experiences downtime or the developer is offline, the local proxy will continue to operate normally using the cached rules. 
Telemetry data will be queued locally and sent when the connection is restored, ensuring zero disruption to the engineering team's velocity.

## 3. Permissions and Installation Footprint

**Q: Does the MCP-Shield executable require Administrator (Root) privileges?**
A: **No.** MCP-Shield runs entirely in **Userland**. It does not install kernel drivers, does not require elevated privileges, and does not modify system registries. It simply sits as a standard `stdio` proxy between the IDE and the MCP servers, running under the same user privileges as the developer.

## 4. Digital Signatures and AV False Positives

**Q: Will our corporate Antivirus or Windows SmartScreen block the executable?**
A: The production releases of MCP-Shield `.exe` and `.dmg` binaries are signed with an **EV (Extended Validation) Code Signing Certificate**. This ensures immediate reputation with Windows SmartScreen and macOS Gatekeeper, preventing false positives from EDR solutions like CrowdStrike or SentinelOne.

## 5. Safe Rollback (Uninstall)

**Q: If we deploy this and want to roll it back, will it break our developers' existing AI configurations?**
A: **No.** MCP-Shield includes a zero-friction uninstall command:
```bash
mcp-shield uninstall claude
```
This command automatically and atomically restores the configuration file (`claude_desktop_config.json` or Cursor equivalent) to its exact prior state, removing the proxy wrapper. It is completely safe to deploy and revert via centralized MDM tools.

## 6. Reporting a Vulnerability

If you believe you have found a security vulnerability in MCP-Shield (the client proxy, the standalone binaries, or `mcp-shield-server`), please report it **privately** to:

**[GitHub private vulnerability reporting](https://github.com/jaumerohi2007-cell/mcp-shield/security/advisories/new)** — open a draft security advisory on the public `mcp-shield` repository (English and Spanish accepted). This single channel covers both the client and `mcp-shield-server`.

Please include, where possible:
- The affected component and version (`mcp-shield --version` or the server release).
- Steps to reproduce, a proof of concept, or the relevant configuration.
- Your assessment of the impact (e.g., policy bypass, data egress, privilege escalation).

### Our commitment (coordinated disclosure)

- We will acknowledge your report within **2 business days**.
- We will triage the issue, keep you informed of progress, and target a fix or mitigation for confirmed vulnerabilities within **90 days** (faster for critical issues affecting the policy engine or data-egress guarantees).
- We ask that you do **not** disclose the issue publicly until a fix has been released and we have coordinated a disclosure timeline with you.
- We are happy to credit researchers who report in good faith, unless you prefer to remain anonymous.

Good-faith security research performed within these guidelines is welcome; we will not pursue action against researchers who respect user data and avoid service disruption while investigating.

A machine-readable version of this policy is published as `SECURITY.txt` at the root of this repository, following [RFC 9116](https://www.rfc-editor.org/rfc/rfc9116).
